# 1. Executive Summary

- `hexo-mantis` is a large, strongly tested Rust/Python system. Its live `run6` path is **regular PUCT**, not Gumbel MCTS: 50 neural-network leaf evaluations per move, root Dirichlet noise, constant temperature 0.5, raw temperature-shaped visit targets, a 100,000-position graph replay ring, and a four-layer/128-wide `GnnArchV2`.
- The highest-priority defect is optimizer safety. Gradient finiteness is checked only after clipping and `optimizer.step()`. In the BF16 graph path used by run6, a finite loss with non-finite backward gradients can corrupt model and optimizer state before the warning is emitted.
- Arena moves are not checked against `legal_moves()` before `Board.apply_move`; that primitive checks occupancy but not the opening/radius rule. A faulty external opponent can therefore play an out-of-rule move and still receive a scored result.
- Resume semantics are internally inconsistent: nested launch config sections overwrite checkpoint-owned configuration, while the checkpoint-stamped architecture and restored optimizer may continue to represent the old run. Full v2 weights are also loaded with `strict=False`.
- A resumable state is not one atomic artifact. Checkpoint and canonical replay-ring writes are direct, only the small sidecar is atomically replaced, and periodic checkpoints have no ring/sidecar. A periodic `--resume-from` logs the missing sidecar, then restores learner state while starting with an empty replay and reset evaluation state.
- Run6 search truncates every node to the top 192 network-prior actions. The root network scores all 216 legal actions immediately after the opening stone, but expansion then removes 24 before PUCT visits, Dirichlet noise, target mass, or move selection.
- Fifty PUCT leaves is a throughput-oriented baseline, not a demonstrated strength optimum. AlphaZero and MuZero used 800 simulations for board games, while MuZero used 50 only for Atari's explicitly smaller action space; older neural-guided Hex work used 10,000 much cheaper rollout simulations. Those counts do not transfer directly, but they make 50 look sparse for Mantis's 192-action root. A measured 50/96/192 budget frontier is required; 96 is the provisional useful-run choice.
- The implemented Gumbel/Sequential-Halving and Completed-Q paths are dormant in every committed config. Correct Gumbel search is attractive here because it targets policy improvement when simulations are fewer than actions, but Mantis's current hybrid uses PUCT below root, truncates before Gumbel sampling, loses budget remainder, uses searched root `W/N` instead of raw root value, and omits official Mctx-style Q range normalization. It should be repaired and A/B tested, not enabled as-is.
- Promotion games are correctly seat-swapped and compute-matched, but the CI resamples individual games rather than opening pairs and repeated evaluation has no sequential error control. Under a simplified independent 50/50 no-draw null, the 208-game full gate has about a 2.2% false-promotion probability per eligible look; 19 independent looks would be about 34.5% cumulatively.
- The closest recorded run6-shaped measurement reports 1,581 learner steps/hour and 1,627 games/hour. A steady evaluation occupied about 40% of one 1,000-step interval and a full confirmation round about 82%; evaluation duty cycle is already material.
- Shrimp offers useful patterns—canonical action ranks, rule-enforcing submissions, mover-aware returns, true pair-level evaluation statistics, strict model-config loading, and temporary-file checkpoint publication—but its training method, rules, and model contract differ. Its current native MantisNet bridge is also incompatible with the current Python model and should not be copied as a working integration.

The intended dependency direction is sound: Rust rules → encoding/graph/search → self-play → PyO3 bridge; Python config/model/self-play/train/eval are composed only at `mantis.run`. Representation tags are explicit, and graph/grid mismatches generally fail closed.

### Training and self-play flow

1. `mantis.run.main` loads exactly one YAML through duplicate-key-safe `load_config`, validates `RunConfig`, resolves output/resume arguments, and calls `launch_run` (`src/mantis/config/loader.py:76-131`; `src/mantis/run.py:1392-1529`).
2. `build_run_collaborators` seeds Python/NumPy/Torch, resolves the encoding and architecture, builds the learner and replay facade, optionally restores checkpoint/sidecar state, then constructs `WorkerPool` (`src/mantis/run.py:535-625`).
3. `WorkerPool.start` starts one Python inference thread, one Python drain thread, and the Rust runner (`src/mantis/selfplay/pool.py:397-435`). Run6 creates 16 Rust worker threads; each owns a board, MCTS tree, and RNG (`crates/mantis-selfplay/src/runner/spawn.rs:63-113`).
4. Per move, a worker resets its tree to the current board, expands/evaluates the root, selects batched leaves with virtual loss, submits graph requests, blocks for responses, and backs up values (`runner/search_drive.rs:657-1059`). There is no subtree reuse across moves.
5. The shared Python inference server fuses requests from workers up to `inference.inference_batch_size=64` or 10 ms, builds tensors, executes one BF16 `forward_batch`, segment-normalizes legal logits, and returns values/policies (`inference_server.py:770-1013`).
6. The chosen move is sampled from the temperature-shaped root visit policy. A pre-move `GraphRecord` stores stones, sparse legal policy mass, mover, moves remaining, ply, full-search flag, eventual outcome, value-valid bit and game length (`crates/mantis-selfplay/src/replay/hexg/mod.rs:222-245`).
7. Finalization writes terminal `z` from the recorded mover's perspective. Organic draws use `-0.5`; ply-cap rows carry `-0.5` but `value_valid=false`, so they do not enter the value loss (`runner/finalize.rs:94-128,184-216`; `records.rs:725-756`).
8. Python drains completed records, expands them to tuples, and calls back into Rust once per row to insert them into `HexgBuffer` (`src/mantis/selfplay/pool_drain.py:48-225`; `pool_push.py:29-42`).
9. The coordinator converts newly completed game count into at most one optimizer step in run6, samples 256 positions, rebuilds graphs in Rust, partitions by edge/node caps, and performs one accumulated optimizer update (`src/mantis/train/mixing.py:13-16`; `coordinator/dispatch.py:181-350`).
10. Every learner step copies inference weights to the actor. Eval/checkpoint/monitor clocks are learner-step based, not game based (`coordinator/step.py:613-727`).

### Inference flow

- **Self-play:** many Rust game/search threads → one Rust queue → one Python inference server → fused GPU graph batch → ragged policies/values → blocked worker wake-up.
- **Training:** one coordinator thread → Rust parallel replay reconstruction → lazily materialized graph microbatches → one optimizer step.
- **Evaluation:** a spawned child process owns candidate/best `LocalInferenceEngine` instances; up to eight arena game threads share each engine (`src/mantis/eval/worker.py:330-548`; `arena/match.py:195-268`). Candidate and incumbent receive the same `deploy_sims` and leaf-batch width.

### Checkpoint lifecycle

- Fresh model optionally receives the run6 BC representation/policy warm start.
- Periodic full checkpoints contain model, optimizer, scaler, scheduler, config and immutable architecture metadata (`src/mantis/train/checkpoints.py:311-643`).
- Eval serializes candidate and incumbent CPU snapshots. A successful gate copies the exact evaluated candidate into the CPU anchor and replaces `best_model.pt`; actor sync is independent of promotion (`eval/promote.py:1-85`).
- Signal-driven resumable stops additionally persist `replay_buffer.bin` and a JSON sidecar with ring hash/count, eval state, anchor hash, and Python/NumPy/Torch RNG state (`train/resume_state.py:81-348`). Periodic checkpoints do not.

### Parallelism and resource model

Run6 normally has a main learner thread, 16 Rust self-play threads, one inference thread, one replay-drain thread, heartbeat/disk threads, an eval poller, and—during eval—a spawned process with two inference threads and eight arena game threads. Replay graph reconstruction also creates scoped Rust threads. Training/self-play and the eval subprocess contend for the same GPU. This design achieves cross-game batching, but eval concurrency combined with derived graph-build threads can oversubscribe a 24-thread CPU.

### Configuration, logging, tests, reproducibility

- Configuration is strict Pydantic validation of complete YAML; unknown keys are rejected. Resolvers convert validated fields to process-boundary dataclasses (`src/mantis/config/schema/*.py`, `config/resolve/*.py`).
- JSONL events, periodic system/search counters, heartbeat files, eval progress/results and a disk guard provide broad observability. Some settings are nevertheless transport-only or graph-inert; §4 identifies them.
- The tree contains extensive Python and Rust unit/integration/conformance tests, including perspective, target mass, graph-wire, config consumer and lifecycle tests. Default pytest excludes `integration` and `slow`; tracked CI does not exercise the slow tier or a real CUDA run6 lifecycle (`pyproject.toml:45-58`; `.github/workflows/ci.yml`; `tools/ci_gates/run_all.sh`).
- `seed` controls Python, NumPy and Torch, but not native worker or replay RNGs. Reproduction is therefore configuration-level, not trajectory/batch-level (`src/mantis/util/determinism.py`; `runner/game.rs:244-246`; `replay/hexg/mod.rs:335-338`).

## 3.2 Hexo-Shrimp-Bot

### Actual architecture and flow

1. `hexo-engine::Position` is the only authoritative state. Construction is empty/replay-based, legal actions have canonical `legal_rank`/`nth_legal` ordering, and apply rejects illegal opening/radius/occupancy (`crates/hexo-engine/src/position.rs:209-290,382-545`). `hexo-runner::Game::submit` converts rule violations into a forfeit (`crates/hexo-runner/src/game.rs:170-218`).
2. The current practical learner is KLENT. `Collector` maintains a cohort of persistent positions, evaluates them in packed batches, derives a closed-form improved policy from policy logits and action-Q scores, samples one legal rank, and stores every ply of naturally completed games (`python/mantisnet/mantisnet/klent/selfplay.py:76-224`). Capped episodes are dropped from training.
3. A sample is `(move prefix, ply index, chosen legal rank, full improved policy, mover-frame lambda return)`. Prefixes are replayed through the Rust builder for fitting (`klent/selfplay.py:34-50,255-271`; `klent/train.py:119-142`).
4. There is no persistent replay ring. Each iteration collects at least 4,096 completed games by default, trains one shuffled epoch over that in-memory corpus, then discards it (`klent/train.py:29-63`; `klent/run.py:241-258`).
5. The actor objective is policy CE against KLENT's `pi'` plus categorical CE for the taken action's `(positive, negative, zero)` return masses. The exposed state-value head is not trained in this path (`klent/train.py:143-241`).
6. Mover-aware lambda returns derive their sign from actual mover changes, not ply parity (`klent/returns.py:15-61`). This is the right pattern for the game's two-stone turns.
7. Collection for iteration `i+1` overlaps fitting `i` on a copied model snapshot; all GPU calls are serialized by `_gpu_lock`. Fit batches are packed by position count, attention pairs and legal-cell rows and prefetched on four CPU workers (`klent/run.py:190-259`; `fitloop.py:18-244`).
8. Evaluation uses shared random opening prefixes, two color-swapped games per opening, pair-level differences, paired standard error, an exact sign test and Elo intervals (`klent/headtohead.py:97-205,223-380`). Its `gumbel_choose` is an independent-line sequential-halving search, not a tree MCTS (`klent/search.py:18-288`).
9. Python checkpoints atomically rename a temporary `.pt` and strictly compare model config/version on load (`klent/run.py:73-133`). A separate native package format pins encoder/rules/action-order/protocol versions and verifies a behavioral output probe (`crates/hexo-model/src/{manifest.rs,probe.rs,package.rs}`).
10. The native `hexo-bot` architecture is a useful nonblocking session design: worker threads pump states and emit leaves, one batcher owns inference crossings, and one writer owns bounded record publication (`crates/hexo-search/src/session.rs`; `crates/hexo-bot/src/driver.rs`).

### Important limitations

- **Current native bridge is not live-model compatible.** Python `MantisNet.forward(batch, mass_floor)` requires two arguments (`python/mantisnet/mantisnet/model.py:1185-1199`), while `call_inference` passes only `batch` (`crates/hexo-bot/src/mantisnet_python.rs:103-116`). Current `Batch` also requires cell/radius/adjacency tensors absent from the native constructor (`builder.py:667-733`; `mantisnet_python.rs:122-306`). Those defects make the bridge uncallable. Separately, the Rust package intentionally improves from raw `q_values`, whereas Python KLENT improves from mass-normalized `q_score`; that is an algorithm-parity difference, not a malformed raw-output handoff.
- **The current branch is not checkpoint-faithful to its recorded baseline.** `HANDOFF.md:25-34` says the usable `cellnodes-1` checkpoint belongs to an older representation-7 worktree.
- **CI coverage is split poorly.** Rust CI does not run the 48-file Python model suite, CUDA kernels, deck/frontend, or the live PyO3/MantisNet boundary (`.github/workflows/ci.yml`).
- **Resume is not exact.** It restores NumPy run RNG but not persistent collector slots, collector RNG, or Torch RNG; episodes can also span model snapshots because slots persist across iterations.
- **No persistent replay means high freshness but no old-position diversity.** Corpus host memory scales with all plies in the iteration; capped games pay collection cost and are then dropped.
- **Python and Rust nominal ply caps differ:** Python can stop between stones; Rust runner checks only at turn boundaries. Do not mix their results without normalizing semantics.

This is easier to operate than Mantis's 192-leaf schema but offers weaker startup validation and provenance.

### Shrimp search and target details

Self-play is search-free. For each ragged legal segment, it forms

```text
pi'(a) ∝ exp((q_score(a) + tau * log pi(a)) / (tau + lam))
v_hat   = Σ_a pi'(a) q(a)
```

and samples from `pi'` (`klent/improve.py:18-76`; `selfplay.py:146-215`). The critic target is categorical `(max(G,0), max(-G,0), 1-|G|)` on the selected action. This can generate dense policy targets at one forward per position, a major throughput advantage over Mantis's 50 forwards/position, but it relies directly on learned per-action Q accuracy and has no tree correction for tactical errors.

Evaluation `gumbel_choose` samples up to `min(16, sims//2, legal_count)` root actions by raw-logit Gumbel-top-k, extends independent lines by improved-policy argmax, and halves survivors by each line's latest value (`klent/search.py:119-288`). At default `sims=32,m=16`, its schedule does not necessarily reduce to one candidate; final selection reintroduces Gumbel, root logit and transformed latest line value. Repeated line values overwrite rather than average. It is therefore a custom Gumbel-ranked deterministic line search, not tree Gumbel MCTS and not evidence that Mantis should replace PUCT with this implementation.

The Rust package differs again: it exposes improved `pi_prime` as search priors, while Python candidate sampling uses raw logits; the parity fixture can hide this when the difference is only an action-independent offset (`crates/models/mantisnet/src/seam.rs:45-75`; `crates/hexo-search/src/gumbel.rs:224-253`). Shrimp's nonblocking PUCT does support explicit in-flight leaves and virtual loss, but production Python KLENT does not use it.

### Shrimp evaluation, observability and performance

- External matches require an even game count and play one shared random prefix from both seats (`klent/opponents.py:477-548`). Head-to-head groups the two games explicitly and reports marginal Wilson bounds, pair differences, paired/unpaired SE, exact sign-test p and Elo interval (`klent/headtohead.py:97-205`). This is a stronger uncertainty surface than Mantis's individual-game bootstrap.
- Evaluation RNG is derived from run seed and completed iteration. Participant RNG is not carried through the external seat protocol, so crossplay explicitly limits its reproducibility claim (`klent/crossplay.py:907-917`).
- Telemetry uses a transactional SQLite database plus append-only invocation/metrics records; checkpoint publication uses temp + rename but no file/directory fsync (`klent/run.py:73-87,213-310`; `klent/telemetry.py`).
- Collection overlaps fitting, but `_gpu_lock` serializes all model calls. This avoids uncontrolled CUDA concurrency and allows large batches, while limiting overlap when GPU—not CPU—is the bottleneck.
- Samples keep a complete `pi'` vector per ply for all in-memory episodes. Memory is not bounded by fit packing budgets, and capped games consume this storage/compute before all samples are discarded.
- The Python test tree is broad (model shapes, invariance, fit chunking, KLENT returns/eval/deck), and Rust has independent rules/golden/property tests. Current GitHub workflows run Rust gates but omit Python/CUDA/live-bridge tests.

### What Mantis should adopt versus avoid

Adopt/adapt: canonical/versioned action order; checked game submission; mover-transition return-sign tests; pair-unit evaluation statistics; temporary publication plus fsync; strict model-config loading; memory-budget packing invariance tests; behavioral checkpoint probes; and independent rules oracles.

Do not copy: search-free KLENT without a controlled objective change; discarded per-iteration replay as a universal design; unsafe pickle loading; the drifted native Python bridge; a state-value head left untrained while exposed; or the unauthenticated network control plane.

# 5. Search Algorithm Review

## Live run6 algorithm: regular PUCT

At an expanded node, the selected child maximizes

```text
Q + c_puct * P * sqrt(N_parent) / (1 + N_child + virtual_loss_count)
```

For an unvisited child, `Q` is dynamic FPU:

```text
FPU = Q_parent - fpu_reduction * sqrt(sum(prior of visited/in-flight children))
```

If the parent move ends the two-stone turn, child Q is negated; otherwise it remains in the same player's frame (`crates/mantis-search/src/mcts/selection.rs:126-218`). Backup increments node `W,N` and flips sign only when the parent had one move remaining (`mcts/backup.rs:531-551`). First-stone and turn-final terminal values are explicitly distinguished. Perspective tests cover Completed-Q, Gumbel score and root Q (`crates/mantis-search/tests/perspective_parity.rs`). No sign error was found.

Run6 behavior:

- `gumbel_mcts=false`, both Completed-Q flags false.
- 50 NN-served leaves per move; root evaluation is included in that count.
- Root Dirichlet alpha .3 / epsilon .25, skipped for the intermediate stone.
- Batch width 8 with virtual loss only for serial leaf diversification inside a worker tree.
- Constant `tau=.5`; target and sampled move mass are normalized squared visits.
- One worker-local tree allocation is reused, but `new_game(board)` resets tree and TT before every move. There is no subtree reuse.
- TT maps position hash to network evaluation only; transposed paths do not share visits/nodes. Cache-hit backups are not counted as served NN leaves.
- No concurrent shared tree and no cross-worker virtual loss.

### Root action truncation

**Finding**
Every expansion retains only the top 192 legal actions by network prior. Radius 8 has 216 legal cells immediately after the first stone, so run6 drops 24 legal actions before search/noise/target export.

**Evidence**
`MAX_CHILDREN_PER_NODE=192` and `pick_topk_children_ls` sort then truncate (`crates/mantis-search/src/mcts/mod.rs:28-58`; `mcts/backup.rs:43-161`). The radius-8 legal count follows `3r²+3r+1-1=216`.

**Impact**
The search and policy target do not have full legal support. Low-prior tactical moves cannot be recovered by exploration or a Gumbel draw. Retained priors are not renormalized before PUCT.

**Recommendation**
Add truncation-rate/omitted-prior-mass telemetry first. Then test a dynamic/full root action vector or a larger cap specifically on radius 8; do not blindly raise it at all nodes because tree memory and expansion cost increase.

**Confidence: High**
**Location:** `crates/mantis-search/src/mcts/mod.rs::MAX_CHILDREN_PER_NODE`; `mcts/backup.rs::pick_topk_children_ls`.

## Dormant Gumbel and Sequential Halving

The root candidate score is

```text
g(a) + log(max(P(a), 1e-8))
      + (c_visit + max_b N(b)) * c_scale * clamp(Q_root(a), -1, 1)
```

`GumbelSearchState` samples independent Gumbels, selects top `m`, forces root descent into each surviving candidate, and halves the set after phases (`crates/mantis-search/src/mcts/gumbel.rs:39-172`; `crates/mantis-selfplay/src/runner/search_drive.rs:689-845`).

What matches Danihelka et al.: Gumbel-top-m root sampling, equal allocation within a phase, root-perspective Q, `c_visit/c_scale` transformation, repeated halving, and no simultaneous Dirichlet noise.

Material deviations:

1. Below the forced root edge, selection is ordinary PUCT, not the paper/official completed-Q policy-improvement selection.
2. Top-m sampling occurs only after deterministic top-192 prior truncation, not over all legal actions.
3. Unvisited candidates use Q=0 rather than a mixed-value completion.
4. Root evaluation consumes one configured simulation.
5. Integer remainder is discarded. With `N=50,m=16`, the allocation is root 1 + `16×1 + 8×1 + 4×3 + 2×6 = 49`; one unit is unused. Tests pin 49/50 and 599/600 (`crates/mantis-selfplay/tests/served_sims_exact.rs:178-225`).
6. For the first ten relative plies, self-play samples the visit policy rather than selecting the SH winner.

At `N=2`, effective `m=2`, but only one candidate can be searched after root expansion before halving. At `N=1`, no child receives a visit and production target export refuses the search. If this path is revisited, `m=8` would allocate more depth per root candidate at N=50 than m=16, but this is a hypothesis requiring tactical/strength evaluation, not a recommended production change.

## Completed-Q

Mantis computes, for visited root actions, Q from root perspective. For unvisited actions it uses

```text
v_mix = [v_hat + (sumN / visitedPriorSum) * Σ(P(a)Q(a))] / (1 + sumN)
Q_completed(a) = Q(a) if visited else clamp(v_mix,-1,1)
pi_improved(a) ∝ exp(log(max(P(a),1e-8))
                     + (c_visit + maxN)c_scale Q_completed(a))
```

(`crates/mantis-search/src/mcts/completed_q.rs:35-158`; aggregates in `mcts/policy.rs:145-152,331-337`). The softmax, clipping, prior floor, prior fallback and root-perspective conversion are internally consistent.

**Finding**
`v_hat` is the searched root mean `root.w_value/root.n_visits`, not the original network root value expected by the published mixed-value equation.

**Evidence**
`CqAgg.v_hat` is populated from root W/N in `mcts/policy.rs`; the raw initial network value is not retained separately in `Node`.

**Impact**
If enabled, unvisited action values are completed from an already search-averaged quantity and mixed again. Distortion is largest with low simulation counts/many unvisited actions and can make improved targets overconfident or simply different from the intended algorithm.

**Recommendation**
Retain the raw root network value, add paper/official-vector tests, and compare target calibration before enabling. Preserve current `false` settings meanwhile.

**Confidence: High**
**Location:** `crates/mantis-search/src/mcts/completed_q.rs::v_mix`; `mcts/policy.rs` Completed-Q exporters.

Completed-Q cannot currently be enabled by a valid YAML: `train.policy_target` is the single literal `raw_visit_distribution`, and root validation requires that literal and both Completed-Q booleans agree (`src/mantis/config/schema/train.py:536-540`; `schema/core.py:574-593`). At 50 sims the graph visit capacity (57) would also fail the 192-child Completed-Q support requirement. It therefore provides **no benefit under current settings**.

## Evaluation search

`DeployHeadPlayer` performs normal PUCT for `n_sims`, with no Gumbel draw, forced root candidate, or halving. It then deterministically chooses the largest `log P + (c_visit+maxN)c_scale Q`; unvisited Q is zero rather than Completed-Q `v_mix` (`src/mantis/arena/deploy_head.py:37-60,121-164`; `crates/mantis-bridge/src/mcts.rs:503-528`). The correct description is **PUCT plus deterministic Gumbel-style transformed root selection**, not "Gumbel-SH completed-Q."

## Does 50 simulations make sense?

### What external evidence does—and does not—say

- AlphaZero used 800 MCTS simulations per move in chess, shogi and Go during training and greedy 800-simulation evaluation (Silver et al., 2018, Methods "Configuration"). MuZero likewise used 800 in those board games and explicitly used 50 in Atari because Atari had a "much smaller branching factor and simpler policies" (Schrittwieser et al., 2020, Methods "Hyperparameters/Data Generation").
- Anthony, Tian and Barber's neural-guided Expert Iteration on 9×9 Hex used 10,000 rollout/RAVE simulations per move. Those rollouts were much cheaper than one Mantis GNN leaf, and the rules/action space differ, so 10,000 is context—not a transferable target.
- The Gumbel paper's authoritative abstract reports significant improvement with few simulations, and the official Mctx quickstart demonstrates `gumbel_muzero_policy(..., num_simulations=32)` with default `max_num_considered_actions=16`. A demonstration/default is not evidence that 32 or 50 is optimal for this game.
- Official Mctx evaluates the root before its `num_simulations`, schedules the entire budget, uses Completed-Q with the raw root network value, min-max rescales completed Q, defaults to `(50+maxN)×0.1`, and uses the improved selection rule at interior nodes (`mctx/_src/{policies.py,seq_halving.py,qtransforms.py,action_selection.py`). Mantis counts root inside 50, can stop early, does not rescale Q, uses `c_scale=1`, and uses PUCT inside. Numerical budget comparisons are therefore not apples-to-apples.

These sources establish that 50 is not intrinsically absurd—low-budget neural planning can work—but give no basis for calling it enough for Mantis. The closest board-game precedents use far more search, while the main precedent for 50 explicitly relies on a small action space. Mantis has up to 216 legal actions and searches at most 192. After charging one root evaluation, 49 below-root NN evaluations cannot visit even one quarter of that root, and PUCT also spends some of them below depth one. With `tau=.5`, squaring visits further concentrates the target. Early in run6, the BC warm start transfers representation/policy while the value head is fresh, so sparse low-budget value guidance is least trustworthy exactly when training starts.

### Provisional budget recommendation

- **2 simulations:** mechanics-only smoke.
- **50:** preserve as the measured throughput/control arm. It is a plausible minimum-cost baseline, not a strength-oriented recommendation.
- **96:** recommended first useful and provisional long-run budget. It nearly doubles below-root evidence while remaining far below canonical 800-simulation board-game runs. It is divisible by leaf batch 8, although exact divisibility is not required by the PUCT driver.
- **192:** strength-oriented comparison arm after throughput profiling. It is roughly one NN evaluation per retained root action, but some visits go deeper and top-192 still omits legal moves. Do not assume full root coverage.
- **384+:** evaluation/analysis only unless measured marginal Elo justifies the sample-throughput loss. 800 is an external reference point, not a feasible default established for this implementation.

At the recorded 50-leaf rate (1,627 games/hour, 54.5 plies/game), Mantis serves approximately 4.43 million NN leaves/hour. If NN work dominated and throughput scaled inversely—an intentionally simple projection, not a benchmark—the outcomes would be:

| PUCT leaves/move | projected games/hour | projected generated positions/hour | projected learner steps/hour at current coupling |
|---:|---:|---:|---:|
| 50 (measured) | 1,627 | 88,672 | 1,581 measured |
| 96 | ~847 | ~46,183 | ~823 |
| 128 | ~636 | ~34,637 | ~618 |
| 192 | ~424 | ~23,092 | ~412 |
| 384 | ~212 | ~11,546 | ~206 |
| 800 | ~102 | ~5,542 | ~99 |

Fixed CPU/training costs and batching make real scaling non-linear. More simulations may improve each target but reduce games, positions, replay turnover and learner updates per wall-clock hour because updates are coupled to completed games. The objective is therefore **downstream Elo per GPU-day**, not maximum single-move strength or leaves/game.

**Finding**
There is no evidence in the repository or literature that 50 is the strength/cost optimum for Mantis; given the action count, it is best treated as the measured low-budget control.

**Evidence**
Only at most 49 below-root NN evaluations remain after root evaluation, versus up to 192 retained actions. Board-game literature uses much larger budgets, while the authoritative 50-simulation precedent is Atari. Repository evidence measures throughput at 50 but does not provide a controlled search-budget Elo curve.

**Impact**
Keeping 50 may produce sparse, prior-dominated targets; raising it without measurement can halve game/sample/update throughput and make learning worse per day despite stronger individual moves.

**Recommendation**
Use 96 provisionally for the first useful run, but select the long-run value from the frozen-checkpoint and equal-GPU-hour frontier below. Retain 50 if 96 does not provide enough paired strength/target-quality gain to offset throughput.

**Confidence: High that 50 is unvalidated; Medium that 96 is the best provisional point**
**Location:** `configs/run6.yaml`; `crates/mantis-selfplay/src/runner/search_drive.rs`; measured data at `docs/governance/RULINGS_ACTIVE.md:7197-7210`; external sources in §13.

### Required measurement before choosing the long-run budget

1. Freeze early, mid and late checkpoints. For each, run PUCT at 25/50/96/192/384 leaves on identical paired openings against one fixed 384-leaf reference and fixed external baselines. Report paired effect and CI, not only aggregate WR.
2. For each budget, record NN leaves/s, completed games/h, generated positions/h, learner steps/h, GPU utilization, queue wait, inference batch occupancy, graph-build/fuse/H2D time, root distinct-action visits, depth percentiles, TT-hit backups, top-192 truncation rate and omitted prior mass.
3. Run equal-GPU-hour training comparisons at minimum 50 vs 96; use multiple seeds after native RNG is made controllable. Compare fixed-budget evaluation Elo, policy entropy/KL, cap/draw rate and sample-age distributions.
4. Select the Pareto point. A larger budget is justified only if its downstream strength gain exceeds the opportunity cost from fewer independent games/positions and updates. No repository or paper result currently establishes that threshold.

### Is Gumbel + Completed-Q worth it?

**Potential benefit:** yes, as an experiment after repair. Mantis is exactly the regime motivating Gumbel AlphaZero: simulations (50–96) are much fewer than root actions (up to 192 retained/216 legal). Sampling root actions without replacement and allocating them by Sequential Halving can prevent ordinary visit targets from being dominated by whichever prior actions PUCT happens to touch. Correct Completed-Q produces a dense policy-improvement target over legal actions and avoids teaching literal zero probability merely because an action was unvisited. It may therefore reach comparable target quality at fewer leaves and recover games/hour.

**Downsides and risks:**

- The guarantee depends on the intended algorithm and correctly evaluated Q; Mantis currently has neither exact interior selection nor the correct raw-root mixed value.
- Mantis does not min-max normalize Completed-Q as official Mctx does. With `c_visit=50,c_scale=1`, a raw Q difference of only .02 changes a logit by roughly one before `maxN` growth; official Mctx defaults to range-normalized Q and `value_scale=.1`. Current targets could become prematurely sharp.
- Completed-Q fills every unvisited action from a value estimate. That reduces variance but introduces model bias; with run6's fresh value head, incorrect completion can reinforce a bad prior across many unsearched actions.
- Top-192 truncation occurs before Gumbel sampling, so 24 legal radius-8 moves still have zero chance and zero target mass. This breaks the full-action sampling-without-replacement rationale.
- At 50/16, each initial candidate receives only one forced simulation and the code wastes one budget unit. Halving decisions are then driven by high-variance leaf values. Eight candidates are more plausible at 50; 16 become more defensible around 96+, but both require measurement.
- Dense improved targets can overfit correlated value errors; regular PUCT visits are sparse/noisy but reflect actual search allocation. Gumbel also changes exploration distribution, target semantics and action selection simultaneously, making attribution harder.
- Existing checkpoint/replay schema, graph visit capacity, and trainer validator intentionally prevent Completed-Q. Enabling it is a format/experiment change, not a one-line flag.

**Finding**
Correct Gumbel + Completed-Q is worth a controlled experiment for Mantis's low-budget/high-action regime, but the present implementation is not suitable for a long run.

**Evidence**
The algorithm is designed for fewer simulations than actions, but Mantis truncates before sampling, uses PUCT internally, uses searched W/N for completion, omits Mctx-style Q normalization, wastes budget remainder, and cannot enable Completed-Q through schema. Run6 also begins with a fresh value head.

**Impact**
A corrected implementation could improve target coverage and strength per NN evaluation; the current one can instead amplify biased/noisy values and emit a policy different from the intended algorithm.

**Recommendation**
First sample from the full legal root, retain raw root value, normalize/scale Q deliberately, use completed-Q interior selection, consume the exact budget, export the completed improved policy, and add Mctx parity vectors including N=2/8/32/50/96 and legal counts above 192. Then compare corrected Gumbel `{N=32,m=8}`, `{N=64,m=8}`, and `{N=96,m=16}` against PUCT 50/96 at equal NN evaluations and equal GPU-hours. Adopt only if it improves paired Elo per generated-position cost across early and mature checkpoints—not merely if it wins at equal simulations.

**Confidence: High on implementation gaps; Medium on potential training benefit**
**Location:** `crates/mantis-search/src/mcts/{gumbel.rs,completed_q.rs,policy.rs,selection.rs}`; `crates/mantis-selfplay/src/runner/search_drive.rs`; `src/mantis/config/schema/{selfplay.py,train.py,core.py}`.

### Explicit answers

- **Is 50 internally consistent?** Yes for the active PUCT path. It means 50 served network leaves including root, not 50 conventional post-root simulations. It is inconsistent with claims that run6 uses Gumbel-SH.
- **Too low, reasonable, or high?** Reasonable only as a throughput-oriented baseline and probably low for strength-oriented training given a 192-action retained root; the evidence is insufficient to call it definitively too low. The repository has no controlled budget/strength sweep. Use 96 provisionally, with 50/96/192 measured as a frontier.
- **Does search use the simulations well?** PUCT clamps requests to the remaining budget and normally serves 50 NN leaves; it can stop below that count when no uncached distinct leaf is returned or shutdown intervenes. TT hits add backups without NN cost. The dormant Gumbel allocator wastes remainder and spreads N=50 thinly over m=16.
- **Would another root action count help?** Possibly. For dormant Gumbel, m=8 gives more depth per candidate; for PUCT, the 192 cap preserves breadth but causes legal omission. Both changes require paired tactical and strength tests.
- **Does Completed-Q help now?** No; it is off and schema-inaccessible.
- **When could it mislead?** Low N, many unvisited actions, substantial top-192 omitted mass, or a poor searched `v_hat`; all occur or can occur in current geometry if it were enabled.
- **Is eval comparable to self-play?** Candidate and incumbent are compute-matched to each other, but eval is not the same policy: 150 vs 50 leaves, no Dirichlet, deterministic transformed-Q selection vs stochastic squared-visits. It is fair for promotion, not an on-policy reproduction of self-play.

## Shrimp search as a comparator

Shrimp separates three algorithms that should not be conflated:

- Production Python self-play has no tree search. `improved_policy` makes one regularized policy update from learned action-Q for every state.
- Python evaluation uses independent root lines. It has no shared subtree, transposition statistics, visit-count target or backup average; each surviving line is deepened greedily and keeps only its latest value.
- Rust `hexo-search` separately implements nonblocking PUCT with virtual loss/in-flight limits and a Gumbel session, but the live Python learner does not call it.

At default `eval_sims=32`, Python samples at most 16 candidates because `candidate_count=min(16,sims//2,legal_count)`. Its `_halving_schedule` spends 16 deepenings at 16 candidates, eight at eight, and eight at four; it then has four survivors, not one. The final score reintroduces `gumbel + root_logit + transformed latest value` (`python/mantisnet/mantisnet/klent/search.py:36-72,119-288`). This gives broad, cheap tactical probes but does not average value noise or reuse common prefixes. Mantis should borrow Shrimp's explicit paired benchmarking and ragged/full-action discipline—not infer that this 32-step line search proves 32-tree-simulation strength.

**Finding**
Shrimp's Python and Rust Gumbel variants are useful testbeds but not one proven algorithmic reference.

**Evidence**
Python samples from raw logits and ranks halving by latest line value; native package supplies improved policy as priors and Rust search consumes it (`klent/search.py:119-268`; `crates/models/mantisnet/src/seam.rs:45-75`; `crates/hexo-search/src/gumbel.rs:224-253,369-378`).

**Impact**
Copying either implementation into Mantis would import different target and value assumptions and would not repair Mantis's own Completed-Q path.

**Recommendation**
Use official Mctx/paper invariants as the algorithm oracle, and use Shrimp only as an engineering comparison for batching, pair tests and action ordering.

**Confidence: High**
**Location:** Shrimp paths above.

# 6. Training Pipeline

## Sample, replay and target behavior

- One sample is a pre-move position with a full retained legal-set policy over searched children and a terminal mover-frame value. Policy mass is validated finite/nonnegative/normalized before ring insertion (`crates/mantis-selfplay/src/records.rs:618-756`).
- Graph replay samples with replacement. `recency_weight=0`, so the full ring is uniform. The default weight schedule is also uniform.
- Live graph inserts use `game_id=-1`, while the sampler explicitly excludes `-1` from same-game duplicate rejection (`src/mantis/selfplay/pool_push.py:31-48`; `crates/mantis-selfplay/src/replay/hexg/sample.rs:101-129`). Correlated positions from one game can therefore share a batch.
- Warm-up at one row permits severely correlated early updates. At steady state, measured run6-shaped production generated 6,504 games and 6,321 updates in four hours: 0.972 updates/game. At 256 rows/update and 54.5 plies/game, this is approximately 4.57 sampled rows per newly generated row.
- A full 100k ring turns over in roughly 1.13 hours at the measured rate. Once full, a newly completed 54.5-ply game contributes only ~0.14 expected rows to the next uniform 256-row batch.
- `train.augment` is the real graph D6 transformation at sampling (`hexg/sample.rs:152-205`). It is false. `selfplay.rotation_enabled` draws a symmetry but graph inference/recording do not use it; the run currently has no effective graph augmentation.
- Graph loss is ragged policy cross-entropy plus masked 65-bin outcome cross-entropy. No auxiliary losses or entropy regularization are active (`src/mantis/train/losses.py:37-205`; `trainer/core.py:657-695`).
- AdamW excludes biases/1D parameters from weight decay. Graph uses BF16 autocast without GradScaler, accumulates cap-bounded microbatches, clips once, then schedules/EMA/checkpoints (`trainer/core.py:92-111,206-246,603-749`).

### Correlation and freshness finding

**Finding**
The replay contains game IDs but production graph insertion discards them, defeating same-game batch deduplication; warm-up is only one row.

**Evidence**
`push_graph(... game_id=-1)` in `src/mantis/selfplay/pool_push.py:29-42`; `-1` exemption in `crates/mantis-selfplay/src/replay/hexg/sample.rs:101-129`; `train.min_buf_size: 1` in `configs/run6.yaml`.

**Impact**
Early updates are highly correlated, and steady batches can overrepresent long games. No metric reveals unique games, actor age, or row age per batch.

**Recommendation**
Carry the actual game ID through Rust result records and PyO3 bulk insertion; raise warm-up to at least 4,096 positions for useful runs; log unique games and age quantiles per batch.

**Confidence: High**
**Location:** paths above; `crates/mantis-selfplay/src/replay/hexg/sample.rs::sample_graph_batch`.

### Training-rate assessment

Current 0.972 updates/game does not imply 1:1 new/replay data: each game contributes dozens of rows and each update consumes 256 sampled rows. The observed 4.57 replay draws per generated row is not obviously over- or under-training without loss/strength curves. It is high enough that a one-row warm-up is unjustified and low enough that simply reducing learner steps could underuse GPU capacity. Keep the current ratio until sample age, unique-game count, policy KL and held-out strength are measured.

### Checkpoints and recovery

Periodic checkpoints restore model, AdamW, scheduler, scaler and step, but no replay/eval/RNG sidecar. Signal-driven stops attempt to save the ring and sidecar. Rust worker/replay RNGs are neither seeded from config nor captured. Full continuation is therefore not exact even on a clean stop.

## Shrimp training-pipeline comparison

Shrimp optimizes a materially different data distribution:

- `Collector` advances 1,024 persistent slots in lockstep until at least 4,096 games finish. A completed natural game contributes every ply; a capped game contributes zero samples (`klent/selfplay.py:76-224,255-271`).
- Each sample stores the whole episode's move tuple plus index, selected legal rank, dense ragged `pi'`, and mover-frame lambda return. Fitting reconstructs the prefix through the authoritative Rust encoder. This reduces stored graph duplication but repeatedly rebuilds positions.
- `signs_from_moves_remaining` derives return sign from actual turn transition, avoiding the common two-stone parity bug. Mantis terminal `z` is also perspective-correct, but any future bootstrapping should copy this explicit mover-transition method.
- One epoch consumes the new corpus and discards it. This removes stale replay and makes train/new accounting simple, but loses long-horizon diversity and makes host memory proportional to all collected policy vectors. Mantis's ring is preferable for sustained self-play if game IDs/age are added.
- Collection for the next iteration uses a copied pre-fit model while the current corpus trains. Long-lived slots can therefore contain actions/bootstrap values from more than one actor snapshot. Mantis instead syncs actors each learner step but should record actor version per sample.
- Packing by padded attention pairs and legal rows, followed by sample-weighted gradient accumulation, makes memory limits semantically explicit. Tests check chunking invariance; Mantis should adopt that style for cap changes.
- Shrimp's action critic is trained only on the selected action's categorical lambda return. Unselected Q values influence `pi'` without direct same-state targets, creating potential extrapolation bias. Mantis's state-value target is lower-dimensional but its 50-leaf PUCT policy is expensive and sparse.
- Shrimp checkpoints publish by temporary rename and strictly compare model config/version, but omit Torch/collector state and use unsafe pickle loading. Mantis's envelope is richer; neither repository currently provides a fully durable, exact continuation.

A direct "which trainer is better" conclusion is unsupported. For Mantis, the actionable comparison is to instrument target entropy, calibration and Elo per inference: PUCT visits versus a corrected Gumbel Completed-Q target versus a separately implemented KLENT action-Q branch. Mixing these objectives in one run would make attribution impossible.

# 7. Evaluation Audit

## Exact run6 protocol

- **Trigger:** asynchronous kick at learner steps divisible by `train.eval_interval=1000`; a still-running round causes the boundary to be skipped, not queued (`src/mantis/train/coordinator/step.py:680-727`; `eval/pipeline.py:650-696`). Gate runs every eval round because `stride=1`.
- **Strength floor:** 4 candidate-vs-random games at 96 sims. At least one decisive game is required; min win rate is 0.
- **Promotion screen:** 80 candidate-vs-current-best games at 150 sims on both sides.
- **Confirmation:** 128 additional games if screen WR ≥ .44. Screen and confirm are pooled, for 208 games.
- **Ladder:** nominal six rungs, but only SealBot d5 resolves; its cap is 32 games at 128 candidate sims. SealBot uses a fixed depth, so compute is not equal in the same unit.
- **Random floor:** 20 games at 96 candidate sims.
- **Pairing:** each selected four-ply book opening is played with candidate in both seats. Gate counts are even and exact. Odd counts in other configs are rounded to opening pairs or sliced, which can violate declared counts/pair integrity.
- **Exploration:** no Dirichlet or sampling; final move is deterministic transformed-Q argmax. CUDA kernels are not fully deterministic and concurrency changes batching order.
- **Promotion:** exact evaluated candidate snapshot replaces the best anchor when raw pooled WR ≥ .55, bootstrap lower WR bound > .50, and low-power check passes (`src/mantis/eval/aggregate.py:211-325`; `eval/promote.py`). Draws score .5; capped games are draws.
- **Metrics:** gate WR/counts/CI proxy/effective n; rung W/L/D/WR/bootstrap CI; BT ladder ratings and channel metrics. Gate result does not retain full W/L/D composition, and `best_model_step` is discarded in round-spec construction.

## Statistical resolution and uncertainty

At true score 50%, an independent-game binomial approximation gives:

| Block | n | draw-aware score quantum | win quantum | approximate 95% margin |
|---|---:|---:|---:|---:|
| Floor | 4 | 12.5 pp | 25 pp | ±49.0 pp |
| Random floor | 20 | 2.5 pp | 5 pp | ±21.9 pp |
| Ladder rung | 32 | 1.5625 pp | 3.125 pp | ±17.3 pp |
| Gate screen | 80 | .625 pp | 1.25 pp | ±11.0 pp |
| Gate pooled | 208 | .2404 pp | .4808 pp | ±6.8 pp |

These margins understate uncertainty if the two legs of an opening are positively correlated. The code calls `pair_bootstrap_wr_ci`, but `_agg_record` drops `opening_id`, `_distinct_outcomes` yields one value per distinct individual trajectory/seat, and bootstrap indices select those individual games independently (`src/mantis/eval/worker.py:241-264`; `eval/aggregate.py:67-147`).

Under a simplified independent, no-draw, 50/50 null, a percentile lower bound first clears .5 around 119/208 wins. `P(X≥119)≈2.204%`; the screen escalation bar itself passes about 84.285% of null screens. For `k` independent eligible looks, the illustrative family-wise probability is `1-(1-0.02204)^k`; `k=19` gives about 34.5%, but 19 is not a limit encoded by run6. Real rounds share openings, models and moving anchors, so this is an illustration—not a calibrated run-level probability.

## Cost

Repository-recorded run6-shaped evidence (`docs/governance/RULINGS_ACTIVE.md:7197-7210`) reports:

- 1,581 learner steps/hour; 1,627 games/hour; mean 54.5 plies/game.
- 900.6 s steady evaluation and 1,872.8 s full 264-game escalated evaluation at concurrency 8.
- 1,000 learner steps took about 2,277 s. Thus eval was active for approximately 39.6% of a steady interval or 82.2% of a full interval. It runs concurrently, so this is duty cycle, not proof of equal training slowdown.

### Promotion-statistics finding

**Finding**
Automatic promotion is not pair-clustered and has no repeated-look error control; fixed seeds reuse opening samples across rounds.

**Evidence**
`opening_id` exists in `arena/match.py::GameRecord` but is omitted by `eval/worker.py::_agg_record`; `eval/aggregate.py::_distinct_outcomes,pair_bootstrap_wr_ci` independently resample games. `eval.gate.seed_base` is constant each round.

**Impact**
Confidence can be too narrow when paired legs correlate, and a nominal per-round 95% rule does not bound false promotion over a long sequence. Adaptive screen selection plus pooled screen data complicates interpretation further.

**Recommendation**
Carry opening ID, aggregate each two-leg pair to one pair score, resample pairs, and adopt either a preregistered one-shot gate, an always-valid confidence sequence, or alpha spending. Use round-derived non-overlapping book subsets. Until then, require manual promotion review.

**Confidence: High**
**Location:** `src/mantis/arena/match.py::GameRecord`; `src/mantis/eval/worker.py::_agg_record,_play_gate_block`; `src/mantis/eval/aggregate.py::_distinct_outcomes,pair_bootstrap_wr_ci,aggregate_gate`.

## Recommended evaluation protocol

After the statistic is fixed:

- Evaluate every 5k–10k learner steps; run the expensive promotion gate no more often than every 25k–50k steps.
- Use 64–128 distinct paired openings (128–256 games) for screening and another non-overlapping 128 pairs for confirmation.
- Give candidate and incumbent the same architecture, encoding, device, search implementation, leaf width and served-leaf budget while loading their distinct candidate and incumbent checkpoint weights; disable noise and sampling.
- Keep fixed RandomBot and SealBot d5 health baselines, plus a small stratified set of historical checkpoints. Remove unresolvable ladder rows.
- Report pair scores, W/L/D, cap rate, paired SE/CI, effect size, total compute and opening IDs. Track Bradley–Terry/Elo for trends, not as the sole promotion rule.
- Treat promotion as a sequential decision with an explicit error budget; do not infer confidence by multiplying nominal per-round CIs.

## Shrimp evaluation comparison

Shrimp's head-to-head design is the clearest component for Mantis to adapt. `shared_openings` emits pair-major schedules and enforces even game counts; `paired_statistics` validates exactly two legs, computes each pair's score difference, paired and unpaired standard errors, an exact two-sided sign test over decisive pairs, and an Elo interval when pair variance is estimable (`python/mantisnet/mantisnet/klent/opponents.py:477-548`; `klent/headtohead.py:97-205`). It also warns rather than inventing an interval for one pair or zero pair variance.

Limitations remain. In-driver evaluation occurs only at configured iteration boundaries and does not itself promote a model. External opponents can have time/depth budgets that are not equivalent to model simulations. Capped games score .5, participant RNG is not controlled by the crossplay protocol, and the same run seed/iteration derivation can repeat schedules across opponent channels. The fixed-reference h2h path is more diagnostic than comparing only adjacent checkpoints; the crossplay Bradley–Terry path is useful for long-term trend, provided rules and participant versions match.

For Mantis, adopt the **unit of analysis**, not just Shrimp's formulas: preserve opening ID and two legs together, report pair-level effects and exact sign counts, include at least one fixed historical reference, and keep promotion separate from descriptive Elo. Mantis already has better subprocess isolation and compute matching between candidate/incumbent, so those pieces should remain.

# 8. Correctness Findings

## P0-1 — both live learners can mutate on non-finite gradients

**Finding**
Gradient finiteness is checked only after optimizer mutation in both repositories.

**Evidence**
In Mantis, `clip_and_step` calls `clip_grad_norm_` then `optimizer.step()` (`src/mantis/train/losses.py:382-399`), and the graph trainer inspects `math.isfinite(grad_norm)` afterward (`src/mantis/train/trainer/core.py:713-729`). Run6 graph AMP is BF16 with no GradScaler overflow skip. In Shrimp, `fitloop.py:229-231` calls `optimizer.step()` before `_refuse_nonfinite_parameters`.

**Impact**
A finite forward loss whose backward produces Inf/NaN can corrupt weights and optimizer state before either system reports or raises. Mantis can also scale otherwise finite gradients by a non-finite clip coefficient.

**Recommendation**
Check finite loss and gradients before any clip/step mutation; unscale first when applicable; on failure clear gradients and abort/skip without advancing optimizer, scheduler or step. Add custom-autograd NaN-gradient regression tests in both repositories.

**Confidence: High**
**Location:** Mantis `src/mantis/train/losses.py::clip_and_step`, `src/mantis/train/trainer/core.py::train_step_from_graph_batch`; Shrimp `python/mantisnet/mantisnet/fitloop.py::fit_epoch`.

## P0-2 — arena accepts moves outside the rules legal set

**Finding**
Arena opening and player moves bypass an explicit legal-set check.

**Evidence**
`_play_one_game` directly calls `board.apply_move` (`src/mantis/arena/match.py:96-125`). Native `Board::apply_move` rejects occupancy but deliberately does not enforce radius/opening legality (`crates/mantis-core/src/board/state/core.rs:482-496`).

**Impact**

**Recommendation**
Before every replayed opening and selected move, check membership in the authoritative legal set. Treat player illegal moves as a named forfeit and invalid opening-book moves as fatal corpus errors.

**Confidence: High**
**Location:** `src/mantis/arena/match.py::_play_one_game`; `crates/mantis-core/src/board/state/core.rs::apply_move`.

## P0-3 — nested resume config and effective runtime can disagree

**Finding**
Checkpoint-owned keys are legacy flat names, but production overrides complete nested sections and then builds from mixed authorities.

**Evidence**
`RESUME_CHECKPOINT_OWNED_KEYS` lists flat `lr`, `encoding`, etc.; `init_trainer` passes nested `RunConfig` with `declared_keys=None`; `apply_config_overrides_f1` updates whole top-level sections (`src/mantis/train/orchestrator.py:21-31,112-125`; `train/checkpoints.py:994-1053`). **Impact**
A resumed checkpoint can carry a new config identity while running an old architecture/optimizer state; worker encoding and learner metadata may disagree. Future artifacts can misstate provenance.

**Recommendation**
Define checkpoint-owned nested paths, compare identity/architecture/encoding strictly, permit only explicit documented overrides, and record effective optimizer/scheduler values after restoration.

**Confidence: High**
**Location:** paths above; `src/mantis/train/checkpoints.py::resume_trainer,build_resume_config_overrides`.

## P0-4 — resume bundle is not atomic or immutable

**Finding**
Checkpoint, replay ring and sidecar are written separately; checkpoint/ring writes are direct and every sidecar references one mutable canonical ring.

**Evidence**
Direct `torch.save` to final checkpoint path (`train/checkpoints.py:373-412`); `File::create` truncates `replay_buffer.bin` (`crates/mantis-selfplay/src/replay/hexg/persist.rs:43-104`); only sidecar uses temporary + replace (`train/resume_state.py:272-291`). `load_resume_state` matches `checkpoint_filename` but does not cross-check sidecar `run_id` and `step` against checkpoint metadata (`resume_state.py:294-331`).

**Impact**
Crash/ENOSPC can leave a canonical-looking partial artifact, destroy the prior valid ring, or mismatch ring count/hash and checkpoint. Historical sidecars are not self-contained.

**Recommendation**
Write versioned checkpoint/ring/sidecar files to temporary paths, fsync, verify hashes/counts under one ring snapshot lock, cross-check checkpoint filename/run ID/step, atomically publish a manifest last, and retain at least two complete bundles.

**Confidence: High**
**Location:** paths above; `src/mantis/train/coordinator/step.py::_save_resumable_state`.

### Shrimp resume is not an exact continuation

**Finding**
A resumed Shrimp run restores model, optimizer and one NumPy RNG but not the live collector cohort or all RNG state, and it permits training-recipe changes.

**Evidence**
Checkpoint payload is defined in `python/mantisnet/mantisnet/klent/run.py:73-133`; `run_training` constructs a fresh `Collector` at `190-210`. Torch RNG and collector slots/RNG are absent. Invocation LR is explicitly reapplied after optimizer restoration (`run.py:548-554`).

**Impact**
In-flight episodes vanish and the post-resume data stream differs. A checkpoint is a valid warm continuation of weights/optimizer, not an exact experiment continuation.

**Recommendation**
Persist Torch RNG plus collector positions/episodes/RNG, separate fork from exact-resume CLI semantics, and reject recipe drift for exact resumes while recording intentional overrides for forks.

**Confidence: High**
**Location:** Shrimp `python/mantisnet/mantisnet/klent/run.py::save_checkpoint,load_checkpoint,run_training,main`.

## Other correctness/maintainability observations

### Worker panic propagation

**Finding:** A Rust worker panic stops the runner, but Python's fast producer-health check watches only the drain thread.
**Evidence:** panic handling in `crates/mantis-selfplay/src/runner/spawn.rs:22-52`; health check in `src/mantis/selfplay/pool.py:369-379`.
**Impact:** failure can appear as a stall until the 1,800 s watchdog.
**Recommendation:** surface runner stopped/panic count on every health check and abort immediately.
**Confidence: High**
**Location:** paths above.

### Output-directory ownership

**Finding:** Multiple processes can use the same run output directory without an exclusive lock.
**Evidence:** `src/mantis/run.py:1453-1458`; explicit note in `eval/pipeline.py:526-533`.
**Impact:** best model, replay, ladder, checkpoints and heartbeats can be interleaved or replaced across runs.
**Recommendation:** acquire a process-lifetime lock and bind it to run ID/config hash.
**Confidence: High**
**Location:** paths above.

### Duplicate signal save path

**Finding:** A signal can trigger a coordinator save and then loop final-save at the same learner step.
**Evidence:** `src/mantis/train/coordinator/step.py:565-577`; `train/loop.py:127-170`.
**Impact:** duplicate large writes and confusing provenance during the most failure-sensitive period.
**Recommendation:** make one component own shutdown persistence and emit success only after commit.
**Confidence: Medium**
**Location:** paths above.

### CUDA packaging contradicts run6

**Finding:** run6 requires CUDA while the default dependency source explicitly installs CPU Torch.
**Evidence:** `configs/run6.yaml` `train.device`/`eval.worker_device`; `pyproject.toml:34-41`.
**Impact:** documented environment bootstrap cannot run the production config without an out-of-band replacement.
**Recommendation:** publish a supported CUDA lock/install profile and verify it in a GPU smoke job.
**Confidence: High**
**Location:** paths above.

### Governance/code promotion mismatch

**Finding:** Repository law calls a threat probe mandatory before promotion, but no production promotion call site executes it.
**Evidence:** requirement in `docs/registers/laws.md:55-60`; promotion route in `src/mantis/eval/promote.py` and `train/coordinator/drain.py`.
**Impact:** current promotions do not satisfy the repository's stated acceptance contract.
**Recommendation:** implement the probe as a fail-closed gate or formally amend the law.
**Confidence: High**
**Location:** paths above.

# 9. Performance Findings

## Measured or repository-recorded

1. **End-to-end run6-shaped rate:** 1,581 steps/hour and 1,627 games/hour over four hours; mean 54.5 plies/game (`docs/governance/RULINGS_ACTIVE.md:7197-7210`).
2. **Evaluation duty cycle:** steady 900.6 s and full 1,872.8 s versus ~2,277 s per 1,000 learner steps. Evaluation is a major shared-resource workload.

## Strongly evidenced static hotspots

### Per-row Rust→Python→Rust replay insertion

**Finding**
Completed graph records are expanded into Python tuples and pushed back into Rust one row/call at a time.

**Evidence**
`crates/mantis-bridge/src/runner.rs:477-516`; Python loop in `src/mantis/selfplay/pool_push.py:29-42`; PyO3 insertion in `crates/mantis-bridge/src/hexg.rs:118-164`.

**Impact**
High-multiplicity object allocation and FFI overhead on every generated position; actual percentage is unmeasured.

**Recommendation**
Profile first, then add one bulk Rust-owned transfer/insertion API if material. Preserve validation/counters and benchmark end-to-end games/hour.

**Confidence: High that the crossings occur; Medium that they dominate**
**Location:** paths above.

### Evaluation tree allocation

**Finding**
Each deploy-matched gate game constructs two fresh MCTS trees and each external-bot game one; each tree preallocates one million nodes (~32 MB documented), while self-play reuses worker trees.

**Evidence**
`DeployHeadPlayer.new_game` creates `MCTSTree` (`src/mantis/arena/deploy_head.py:121-127`); `MAX_NODES=1_000_000` and vector fill in `crates/mantis-search/src/mcts/{node.rs,mod.rs}`.

**Impact**
At gate concurrency 8, up to sixteen such trees are active, creating memory-bandwidth/allocation churn. Magnitude is not measured.

**Recommendation**
Measure allocation time/RSS; if material, reset and reuse one tree per thread-local player rather than reallocating.

**Confidence: High occurrence; Medium bottleneck**
**Location:** paths above.

### Artifact growth and synchronous copies

**Finding:** Candidate/best snapshots and full checkpoints are copied to CPU and saved without retention; `DiskGuard` detects low space but does not prune.
**Evidence:** `src/mantis/eval/pipeline.py:792-809`; `eval/snapshot.py:43-72`; `train/lifecycle/disk_guard.py`.
**Impact:** Run6's original one-million-step/1,000-step cadence can create 1,000 learner checkpoints plus eval artifacts and synchronous D2H/I/O pauses.
**Recommendation:** Measure bytes/write latency, retain recent plus milestone bundles, and garbage-collect only after atomic publication.
**Confidence: High on growth; Medium on runtime impact**
**Location:** paths above.

## Plausible bottlenecks requiring profiling

- Per-leaf graph construction/fusion and GINE `[E,128]` intermediates.
- Queue wait, low inference batch fill, H2D copies and Python scheduling.
- Eval CPU oversubscription: 16 self-play workers plus eight games, each potentially invoking derived graph-builder threads.
- `release_cuda_cache()` after each evaluation move.
- Per-sample replay graph reconstruction, state copies and legal/winner routines.
- JSON/event logging at high-frequency diagnostic modes.

Do not revisit legal-set data structure changes without new evidence: repository falsification records report prior regressions (`docs/registers/falsified.md`).

## Shrimp performance comparison

Shrimp's search-free collector needs roughly one network pass per played position rather than 50, so it can generate far more trajectories per inference at the cost of trusting its action-Q head. Its packing model separately caps padded attention pairs and legal rows and prefetches CPU work (`python/mantisnet/mantisnet/fitloop.py:18-244`). Mantis's central inference server already performs stronger cross-worker batching, so replacing it is unnecessary; adding equivalent batch-shape/occupancy reporting is useful.

Shrimp's overlap is constrained by one `_gpu_lock`: next-iteration collection can overlap fitting in host work, but GPU forwards serialize (`klent/train.py:84-116`; `klent/run.py:190-259`). This avoids two CUDA owners fighting unpredictably, unlike Mantis's parent learner/self-play and eval child sharing one GPU, but it can leave less opportunity for concurrent kernel scheduling. Neither design is preferable without utilization traces.

Shrimp's principal static memory risk is the unbounded in-memory iteration corpus: every ply retains `pi'` over all legal actions and capped games are discarded only after completion. Its native driver has bounded queues and reusable arenas, but the live-model bridge is broken, so native throughput claims from mock integration cannot be transferred. Profile Python collection and fitting separately before adopting any of its throughput assumptions.

# 11. Prioritized Improvements

## P0: Correctness

1. Make optimizer steps fail closed on non-finite gradients; do not advance any clock on an all-skipped batch. Add gradient-level, not only loss-level, tests.
2. Enforce authoritative legal moves at arena and bot boundaries; distinguish invalid opening data from player forfeit. Resolve the Mantis/Shrimp opening-rule difference before cross-repo matches.
3. Replace flat resume ownership with strict nested-path compatibility; use strict full-checkpoint model loads and separate warm-start semantics.
4. Publish checkpoint/ring/RNG/eval state as one versioned atomic bundle; make periodic checkpoints valid continuation points or reject them for resume.
5. Carry opening IDs into aggregation, bootstrap seat-swapped pairs as units, and add a sequential/repeated-look promotion policy. Block or manually review promotion until fixed.

## P1: Training Quality

1. Carry real game IDs/model versions into replay; raise warm-up; log row age and unique games per batch.
2. Run the 50/96/192 PUCT frontier and select on paired Elo per GPU-day plus games/positions/steps per hour; use 96 only as the provisional starting point.
3. Add top-192 truncation rate and omitted-prior-mass metrics. Repair Gumbel/Completed-Q to official invariants, then benchmark 32/8, 64/8 and 96/16 at equal NN work before considering adoption.
4. Make graph augmentation controls truthful: disable no-op self-play rotation and run a preregistered `train.augment` comparison.
5. Reduce eval cadence/cost, remove dead ladder rungs, and add fixed historical checkpoints plus pair-level effect estimates.
6. Seed/serialize native worker and replay RNGs. Add deterministic evaluation mode and record effective seeds.
7. Fix reachable grid scalar-value/history/non-finite inference defects before using grid configs for evidence.

## P2: Performance

1. Profile current run6 end to end. Prioritize eval duty cycle, graph construction/fusion, queue fill, replay rebuild and CPU oversubscription.
2. If measured material, bulk-transfer completed graph records directly Rust→Rust through one bridge call.
3. Reuse eval MCTS allocations per thread; measure before changing.
4. Add artifact retention and avoid redundant candidate/incumbent CPU serialization; preserve exact evaluated snapshots.
5. Calibrate workers, inference batch/wait and graph caps jointly for each hardware class. Do not raise caps from VRAM size alone.

## P3: Maintainability

1. Delete or wire dead keys; arch-scope graph/grid-only fields; report declared and effective settings.
2. Add a supported CUDA dependency/lock profile consistent with production config.
3. Add output-directory locking, prompt worker-panic propagation, and single-owner shutdown saves.
4. Bring slow Python/CUDA/live-PyO3 integration into CI on an appropriate runner.
5. Adopt Shrimp's independent rules/action-order oracles and behavioral checkpoint probe, but not its currently broken native bridge.
6. Correct stale "Gumbel-SH/Completed-Q" and config-reachability documentation.
