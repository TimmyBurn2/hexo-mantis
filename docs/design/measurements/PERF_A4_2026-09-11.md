## 2. A4-1 — check 14 with the GIL released (commit `13562ce1`)

Change: `verify_edge_geometry` (`crates/mantis-bridge/src/graph_contract.rs`) takes the six
`as_slice()` borrows and runs the verify inside `py.detach`. No wrapper is needed: `&[T]` is `Send`,
so the compiler proves the closure crosses `detach`; the borrows live in the calling frame for the
whole call. The soundness invariant is the callers': the six arrays are read-only while the check
runs — the server's are fresh per pop (`GraphWire.take()` moves the fused buffers into numpy and
nothing writes them afterwards; `slice_graph_wire` re-bases COPIES of the offset arrays and views
of the rest), the trainer's sample is read the same way. Pin: `tests/bridge/test_graph_wire_adv.py::
test_verify_edge_geometry_releases_the_gil_while_it_runs` measures the main thread's longest stall
while a 3.4 M-edge verify runs on a worker thread against a GIL-holding control (a big-int power):
locally the control stalls the main thread for 99.6 % of its wall, the verify for 0.6 %.

## 3. A4-2 — pinned `non_blocking` H2D, `output_size=`, resident dist65 support (commit `8b54b3e1`)

Change: `collate_graph_batch` stages each of its seven tensors pinned and copies `non_blocking`
(torch's caching host allocator holds each staging block until its copy completes); every
`repeat_interleave` in the forward and the two collate helpers passes the host-known `output_size`;
`decode_binned_value` keeps one resident support per device (built OUTSIDE inference mode — the
first cut cached an inference tensor and the trainer's backward through the shared cache then
raised; `tests/selfplay/test_collate_h2d_pinned_parity.py` pins both the byte-identity of the
device tensors against a pageable copy and the autograd path through the cache). The trainer's
`_segment_softmax` twin carries the same `output_size` (its AST-parity test with the collate's copy
requires it).

Microbench (the investigation's `server_forward_bench.py`, collate rows only — its V1–V3
monkeypatches predate the new signature and were not re-run), box, `collate(off)` = structural
checks + tensor build + H2D **including a `torch.cuda.synchronize()`**: B = 16 0.73 → 0.65 ms,
B = 35 1.22 → 1.11 ms, B = 64 2.35 → 2.03 ms, B = 128 4.74 → 5.56 ms. Faster at every served size
(the regime is B ≈ 35–55), slower at B = 128 where the pin copy of 33 MB dominates; the
pre-registered abort (< −0.5 ms at B ≈ 35) is not met.

## 4. A4-3 — `inference.compile_trunk` (commit `35d7480d`)

Change: a new OPTIONAL schema leaf `inference.compile_trunk: bool` (default `false`, registered in
`OPERATIONAL_DEFAULT_KEYS`, resolver `mantis.config.resolve.compile_trunk`, contract v22). When
`true`, the server builds a SERVER-PRIVATE `torch.compile(model.representation, dynamic=True)` and
hands it to `forward_batch(trunk=)`, a new keyword-only seam on both `GnnNet` and `GnnNetV2`
(`None` — and the eager server passes no kwarg at all — is byte-identical to before). Server-private
because `WorkerPool` is handed the trainer's own module: compiling `model.representation` in place
would have compiled the training forward too. The trainer and the eval child (which builds its own
`InferenceServer` from a hand-built config dict without the key) stay eager.

PARITY, stated: the compiled trunk is NOT bit-exact against eager — Inductor fuses the message pass
and orders the `index_add_` atomics differently. `tests/selfplay/test_compile_trunk.py` (CUDA leg)
measures the device's own identical-code eager null first, then asserts the compiled forward within
bf16 noise (max |Δprobs| < 1e-2, |Δvalue| < 1e-2) and that the shared module's eager forward is
unchanged after compiling the wrapper. Local RTX 3070: |Δprobs| 4.2e-6, |Δvalue| 3.8e-4. The R181
parity legs (`tests/model/test_bf16_parity_nulldist.py`) exercise the eager `forward_batch` only and
are untouched by this key; `false` is the shipped numerics. The dashboard's "Determinism hash" panel
is the LAW-04 trajectory-dedupe hash (`game_complete.game_id_byte_hash`), not a numerics hash.

LAW-18: the `compile` sub-block (`enabled`, Dynamo's `unique_graphs`, `recompile_limit`) rides
`iteration_complete.inference_batching`; the pre-registered abort is `unique_graphs` still climbing
past 8 in a burst.

## 5. A4-4 — the two-thread software pipeline (commit `c888c3b7`)

Change (`src/mantis/selfplay/inference_server.py`): the server thread now only pops, plans, collates
and LAUNCHES — every part's forward, segment-softmax and D2H (`non_blocking` into pinned host
buffers) are queued on the device and a CUDA event recorded — and hands the `_InFlightPop` to a
retire thread (`_PopRetirer`, FIFO), which `event.synchronize()`s (GIL released), runs the finiteness
gate on the HOST copies, submits ONE result per pop against the unsliced `legal_offsets`, hands the
captured check-14 parts to the checker, and produces the heartbeat / `first_inference_served` /
`_forward_count`. A `Semaphore(2)` bounds launched-but-undispatched pops (the one on the device plus
the one being dispatched); the server thread blocks on a third. Failures keep ONE path (`_fail_pop`)
but two arms: a launch failure fails the pop being launched, a retire failure fails the retired pop —
never the other. A check-14 finding latched while a pop was in flight refuses that pop at retire, so
only pops already launched when the finding landed can have been served (the checker-thread suite's
paced batcher now waits for dispatch before pacing on the checker; the "served once, next refused"
claim still holds under that pacing). `stop()` closes the batcher, the loop exits and drains its own
retirer; a loop that already returned is drained from `stop()`.

Why a retire thread and not the first cut's single-thread "retire N after launching N+1": that cut
made dispatch of N wait for the NEXT pop, which is the pop deadline (10 ms) whenever every waiter is
already inside N — the eval child at `concurrency 8`, the deploy head at 1, and 16 workers half the
time. It was replaced before any arm ran on it (its queued arms were cancelled), so no number below
is that design's; the local end-to-end smoke of the retire-thread form (8 workers, 101 steps,
`checker_thread` + `compile_trunk`) stepped cleanly with the `pipeline`/`compile` blocks in every
`iteration_complete`.

Tests: `tests/selfplay/test_pipeline_ordering.py` — per-pop ids and answers across three ragged pops
with distinct uid bases (a transposition would move a whole softmax segment), a simulated OOM on the
second pop failing ONLY its ids while its neighbours are served, and a batcher that hands out one pop
and then blocks as an idle queue would, asserting the pop's result arrives while the server thread is
still blocked (dispatch depends on neither another pop nor the deadline). The seam census
(`test_fused_forward_seam.py::test_fg7_03`) now walks the loop plus its four helpers: ONE
`submit_graph_inference_failure`, ONE `submit_graph_inference_results`, three broad handlers (launch
arm, retire arm, loop guard). The loop-census row (`test_selfplay_census.py`, frozen §Q6) moves
`(1, 1, 0)` → `(2, 1, 0)`: the parts loop is walked at launch and again at retire.

Memory: one FORWARD's activations are resident at a time in the allocator's accounting (the caching
allocator reuses a part's freed blocks for the next part in stream order); what doubles is the input
tensors of the pop in flight (≈ 17 MB at B = 35, ≈ 27 MB at B = 55) plus the pinned output buffers.
