## Method

`iteration_complete.inference_batching` carries CUMULATIVE counters since boot (`occupancy.count`
/ `.total` / `.histogram`, `queue_wait`, `collate`, `pipeline.launch`, `pipeline.gpu_wait`,
`fusion.*`); each figure below is a DIFFERENCE between the last row of one 600-s wall-clock window
and the last row of the previous one, so a window's rate is the window's own. Definitions, each
one producer: pops/s = Δ`occupancy.count` ÷ Δwall (one server thread, so this is also 1 ÷ cycle);
B = Δ`occupancy.total` ÷ Δpops; **leaves/s served** = Δ`occupancy.total` ÷ Δwall — PERF-A4's unit
(`arms_summary.py`: pops/s × occupancy); **sims/s billed** = the row's `sims_per_sec`, which
`pool_drain.py` bills as Δpositions × `effective_sims_per_move` — a DIFFERENT unit, ≈ 1.8× the served
figure, and not comparable to any A4 number; the four ms columns are Δ`total_ms` ÷ Δpops (`launch`
brackets `_launch_pop` — plan, slice, collate, the pinned H2D copies, the forward launch and the D2H
queue — so `collate` is a part of `launch`; `gpu_wait` is the retirer's wait on the pop's CUDA event,
i.e. the device stage per pop, read against the cycle as A4 §5 says); CPU ms/leaf = `launch` ÷ B;
edges/graph = Δ`fused_batch_edges.total` ÷ Δleaves.

**The pop rule, so the histogram reads right** (`crates/mantis-selfplay/src/queues/graph.rs`,
`pop_graph_batch_blocking`): the server's pop wakes when the queue holds `saturation_threshold` =
`batch_size / 2` = **32** leaves (`max_in_flight` is 0 on the server's batcher, so the `min` is
inert) OR when the 10-ms `max_wait_ms` deadline passes, and then takes up to 64. The histogram's
buckets are power-of-two LOWER bounds (`_pow2_bucket`), so with `inference_batch_size 64`: the
**64** bucket is a FULL pop (≥ 64 queued at wake), the **32** bucket [32, 63] is a SATURATION pop —
the design's half-batch wake, not a timeout — and buckets ≤ 16 are DEADLINE pops. "Timeout-vs-full"
is therefore three shares, not two.

**Regimes** by wall clock (STATE item 10): the two strix cells ran beside run8 from the chain's
relaunch 17:00:59 UTC to the net-only cell's end **19:46:41 UTC** (`CELLS`, 8 games in flight on the
same 12-core box, the strix graphs built in Python); from then on run8 ran ALONE (`--follow` polls
only; the gate round at step 3 000 had not fired by 20:54). The 19:39 window straddles the boundary
and is labelled CELLS; the 20:49 window is the stream's partial last one (5 min).

## The readings, one per line of the order

1. **Batch-size histogram, ALONE, pooled over 281 349 pops (19:47–20:54 UTC):** 64-bucket (FULL)
   **14.6 %** · 32-bucket (SATURATION, 32–63) **84.9 %** · 16-bucket **0.4 %** · 8-bucket 5 pops ·
   below 8 none · `empty_polls` **0**. Beside a cell the FULL share is higher (31 %) because the
   server thread is slower and the queue fills further while it collates — a symptom, not a gain.
2. **Timeout-vs-full:** alone, **0.4 % of pops are deadline pops**; 85 % wake at the half-batch
   threshold with 32–63 leaves queued and 15 % find a full 64. The 10-ms deadline is not what
   shapes B; the 32-leaf wake is. `queue_wait` alone reads 2.96 ms mean — the server thread waits
   for the 32nd leaf, not for the clock.
3. **ms/batch against B, in-run:** the run pins B in a 1-leaf band alone (45.6–46.7), so the stream
   yields ONE point on the curve, not a curve: at B ≈ 46, `launch` (the CPU stage) 11.46 ms/pop,
   `gpu_wait` (the device stage) 9.36 ms/pop, cycle 14.44 ms — CPU 0.247 ms/leaf, GPU 0.202 ms/leaf.
   The CELLS windows are NOT B-points (B 53 at a 46-ms cycle is contention). The curve over
   B ∈ {16, 32, 64, 128, 256} is step 3's, standalone.
4. **leaves/s, alone vs beside a cell:** **3,208 vs 1,222 served** (38 %); steps/h 1,035 vs 389
   (38 %). Beside a cell the cycle triples (14.4 → 45.7 ms) and every term of it is CPU: `collate`
   ×7 (3.99 → 27.97 ms), `launch` ×3.1, `queue_wait` at the 10-ms deadline (10.18 ms), while
   `gpu_wait` moves +2 ms (9.4 → 11.4). The cell's 8 in-flight games with strix's Python graph
   building starve the server thread and the 32 workers on the 12-core box; the GPU is not what
   they take. This is R359(e)'s accepted cost, priced: ≈ 1 h of run progress per cell at the
   cell's wall (4 256–5 682 s) × the 62 % rate loss.
5. **What bounds the run alone:** the server thread's cycle is `queue_wait` 2.96 + `launch` 11.46 +

## Why shakedown8 read 3 196 against A4's 3 662 compiled — regime named

- **Same unit.** shakedown8's 3 196 (STATE item 10) is the SERVED figure — run8 alone reads 3 208
  by the same derivation (0.4 % apart; same tree, same config but `run_id`, same idle card). The
  billed `sims_per_sec` (5 735 alone) is a different unit and was never the number compared.
- **The gap is −12.4 %, and it decomposes as fill × cycle:** B 46.3 vs 49.6 (**−6.7 %**) and cycle
  14.44 vs 13.6 ms (**+6.2 %**) — leaves/s = B ÷ cycle, 46.3 ÷ 14.44 = 3 206 ✓.
- **The cycle grew because the graphs did.** Per graph, GPU 0.202 vs 0.158 ms (**+28 %**) and collate
  0.086 vs 0.064 ms (**+35 %**); per pop the CPU stage is flat (11.46 vs A4's implied 11.3 —
  13.6 − 2.27, that arm predates the `launch` timer) and the device stage +1.5 ms (9.36 vs 7.82).
  The regime behind it: run8's games are **88 plies** mean / 75 median (1 164 ALONE games; 44 turns,
  `avg_game_length` 42) against the A4 arm's **32.0 plies/game** — A4's `w32ctc` was a 150-step
  burst from the BC net in run6's regime, run8 plays from the 42k parent — so run8's boards are
  larger and its graphs bigger (651 nodes, 16.1 k edges per graph; the A4 record states no
  per-graph size, so the ratio is not on record).
- **Present but UNSEPARATED (each an ESTIMATE of sign only, none measured here):** A-2's quiescence
  unit is in run8's tree and not A4's (`mcts_quiescence_fires` 83 570 by step 2 — forced descents
  on the worker side, which move the fill term); `train.augment` runs the D6 draw on the trainer
  thread, which shares the GIL with the server thread; `selfplay.search_stats_every 8` records
  per-position search stats on 1-in-8 games; `train.max_train_burst 2`. Which of the four moves the
  −12 % by how much is not readable from the stream; step 3's standalone bench (no trainer, no
  augment, no recorder) reads the server without them.
- **So: A4's number stands and run8's number stands; they are two regimes of one server.** Nothing
  in the stream says the pipeline regressed.
